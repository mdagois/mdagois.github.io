Pop Slide on the Game Boy

This article presents the pop slide, a technique to copy data fast on the Game Boy. It was first introduced to me by Dave VanEe, a reader of Game Boy Coding Adventure. We'll start with a brute force copy that is generic but slow. We'll then move on writing an optimized version of the brute force copy. Finally, we'll see the pop slide, which is the fastest way to copy data, but comes with small drawbacks. By the end of the article, you'll have all the knowledge necessary to choose the right copy method for your game.

This article uses code snippets to illustrate the implementation of the three copy methods. The full commented source code for the samples is available on GitHub. You will also find prebuilt ROMs there, so that you can run the samples without having to build them first. The ROMs have been tested on both the BGB emulator and real hardware.

The samples are written in assembly for the RGBDS toolchain. You should be familiar with programming the Game Boy in assembly in order to follow along with the code samples. To get a strong introduction to Game Boy programming in assembly, I recommend you to check my book, Game Boy Coding Adventure. It is a complete coverage of all the aspects of programming the Game Boy, using a beginner-friendly approach for those new to assembly.

To demonstrate the speed advantage of the popslide, we'll measure the number of cycles required to copy 8 KiB of data into VRAM for each copy method. We'll use BGB's built-in features to take the measurements using the two macros in Listing 1.

ResetClockCounter sets BGB's internal clocks counter back to zero. PrintClockCounter outputs the number of clocks elapsed since the last reset to the debug messages window. There are several important notes concerning the clock value reported by BGB. First, we need subtract 8 from LASTCLKS to account for the overhead of BGB's debug message mechanics. Second, the value is printed in hexadecimal, which you might want to convert to decimal for a more intuitive grasp. Lastly, BGB clocks values do not correspond to the Game Boy M-cycle, and not even to T-cycles. Instead, we need to divide the clocks values by 2 to get M-cycles, and by 8 to get T-cycles, since each M-cycle amounts to four T-cycles.

We basically sandwich the CopyData function between ResetClockCounter and PrintClockCounter. This will display the number of cycles taken by the copy to the debug messages windows each time the sample is run.

Brute force copy

Let's start with the brute force copy. It consists of a loop that copies bytes one by one in each iteration, as shown in Listing 3.

The cost of a single iteration is 13 cycles. Since we copy 8,192 bytes, that makes 106,495 (13 * 8192 - 1 for the last jr) cycles for the loop and a grand total of 106,504 cycles when we add the 9 cycles to set the registers before the loop begins. BGB report s34010 in hexadecimal, or 213,008 clocks. Dividing the clocks by 2 yields 106,504 cycles, which is exactly what was expected.

The second copy method improves the performance over the brute force method in two ways. First, it batches 32 bytes copies in each iteration, avoiding the cycle cost of jr for each byte. Second, it uses a single-byte iteration count, reducing the cost of counting down the iterations of the loop. The main disadvantage of that copy is that it takes more bytes in the ROM, but nowadays, it is usually a better trade-off to optimize for cycles than for bytes. Listing 4 shows the code for the optimized copy method.

The cost of a single iteration is 196 cycles (32 * 6 + 1 + 3) for the copy of 32 bytes. There are 256 iterations (8,192 / 32), which makes 50,175 (196 * 256 - 1 for the last jr) cycles for the loop and a grand total of 50,183 cycles when we add the 8 cycles to set the registers before the loop begins. BGB reports 1880E in hexadecimal, or 100,366 clocks. Dividing the clocks by 2 yields 50,183 cycles, which is again exactly what was expected.

Pop slide

The pop slide method uses a clever stack trick to further improve the copy speed over the performance of the optimized method. First, it sets the stack pointer to point to the start of the data to copy. Then, and that's the clever part, it uses pop instead of ld to retrieve two byte of data at a time. Finally, it copy the byte to the destination using optimized ld [hli], a instructions. The code is shown is Listing 5.

Let's go through measuring the cycles again. The cost of a single iteration is 148 cycles (16 * 9 + 1 + 3) for the copy of 32 bytes. There are 256 iterations (8,192 / 32), which makes 37,887 (148 * 256 - 1 for the last jr) cycles for the loop and a grand total of 37,910 cycles when we add the 13 cycles to set the registers before the loop begins, and the 10 cycles to restore the stack pointer to its original value after the loop. BGB reports 1282C in hexadecimal, or 75,820 clocks. Dividing the clocks by 2 yields 37,910 cycles, which is yet again exactly what was expected.

Conclusion

Mostly for DMG The popslide can be used to copy data anywhere in memory, but in games, it was typically used to copy data during the vblank, where its speed advantage would allow to copy more tile data. While the samples are made for the original Game Boy, the techniques they use are relevant to the Game Boy Color too. However, you should always favor using DMA on the Game Boy Color when applicable, e.g. when copying data to VRAM.
